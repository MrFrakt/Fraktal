## 1. What R5 asked for

"A disposable reference AOI suite runs through the intended Logix Echo or named
isolated-hardware CI path and emits machine-readable results; full base/type
suites then grow with implementation."

Three things had to be true, and each is answered below: the suite had to exist
and be disposable; the CI path had to be **named**, not gestured at; and the
results had to be **machine-readable**, not an engineer's report.

## 2. The suite

The suite promotes the two AOIs S16 proved on hardware to the binding's **first
two reference types**, generated by the *same declaration machinery* rather than
a copy of it — `fraktal_ab_reference_suite.py` imports the declaration functions
from `fraktal_ab_s16_fixture.py`, so "reference type" means the same generator
that produced the evidence, not a lookalike.

| Item | Value |
|---|---|
| Reference type 1 | `FRK_Ref_Module` — the Core §6.1 handshake over a simulated plant |
| Reference type 2 | `FRK_Ref_Mode` — the §6.2 AUTO chain and MANUAL behavior |
| Context UDT | `FRK_T_RefCtx`, **39 `DINT` members, no `BOOL` member** |
| Instances | **two** of the module type (`…ModuleInstA`, `…ModuleInstB`) over two independent contexts, plus one mode owner |
| Program / routines / tasks | 1 / 1 / 1; `FRK_RefTask` PERIODIC 10 ms, watchdog 500, output updates disabled |
| Writable inputs | six: `CommandA`, `AbortA`, `ModeSelectA`, `HoldA`, `FaultA`, `CommandB` |
| Physical I/O references | **0**; embedded `Discrete_IO` inhibited |

**The second instance is the point.** Core is inheritance-free, so AB §5.7's
argument is that base behaviour is proven once against a reference type and
**G-BEGINEND plus G-GENERATED** extend that proof to every other type. An
extension argument that has never been exercised on a second instance is an
assertion. Here the module type is instantiated twice, driven independently, and
the suite carries an on-controller **cross-talk counter** that increments if
instance B ever starts a run it was not commanded to start — so independence is
a controller-side measurement, not a host-side inference.

**It is gate tooling, and it is fenced.** The same scope-exclusion rule that
keeps the S16 fixture disposable guards this one: generation fails if the string
`Recipe`, `ParCfg`, `Manifest`, `Registry`, `Mailbox`, `Traceability` or
`ReleaseReport` appears in the output. Nothing here is authorized to become the
production module library.

### The narrowing, recorded as a narrowing

**One step in that path is a manual, authorized operation: the download.** This
is a deliberate binding narrowing and is recorded as such, not left as silence.

AB §5.7 says an engineer manually pressing Run is not CI evidence, and that rule
is kept intact. What is manual here is **deployment**, not the test run: no human
decides, observes, or reports a single suite row. Regeneration, import, Verify,
canonical round trip, census, suite execution and result harvesting all run
unattended and emit machine-readable output.

Three reasons this is the right narrowing rather than a gap:

1. **The toolchain deliberately cannot download.** No tool in it has that
   capability, by design. AB §11.2.1 keeps the engineering conduit off the
   gateway and not permanently open. A binding that could deploy to a physical
   controller unattended would be a worse binding.
2. **Echo is unavailable**, measured, not assumed.
3. **Automated download does not work on this workstation anyway.** Three
   attempts across two mechanisms all crashed Studio v33 — two with an identical
   null-pointer read inside the shared MFC runtime, and a third, via real
   keyboard input, with a noncontinuable `STATUS_SXS_EARLY_DEACTIVATION` in
   `ntdll`. The controller was untouched every time. Details in
   [`AB_S16_EXECUTION_EVIDENCE_2026-09-06.md`](AB_S16_EXECUTION_EVIDENCE_2026-09-06.md) §4a.

The decision record's **D3** already took this shape of trade once, narrowing
"parity" to the shared contract suite rather than an A/B rig — removing a
hardware blocker without weakening the claim, and saying so. This is the same
move.

**The consequence, accepted in writing:** Fraktal/AB does **not** claim
push-button, zero-touch CI to a physical controller. It claims a reproducible
regenerate-verify-execute pipeline with one authorized human deployment step.

## 10. What R5 does not claim

1. **Not zero-touch CI.** One authorized human deployment step, by design (§3).
2. **Not the full §5.7 harness.** R5 asks for a disposable reference suite and
   machine-readable results; the controller-resident `FRK_TestSuite` /
   `FRK_TestRunner` shape, with per-type suites and JUnit conversion, grows with
   implementation. The five summary fields are emitted here in that shape so the
   conversion has something to consume.
3. **Two reference types, not a type library.** T2/T3/T5 rows and a Unit's T10
   mode-entry policy are not covered.
4. **MANUAL mode is lightly exercised** — the AUTO chain carried the evidence.
5. **`BOOL` members in a public UDT remain unmeasured** — a recorded S12 hole.
